**Status**: Draft  
**Priority（ORM 迁移）**: P0

## 背景与动机

ORM 迁移与建表普遍依赖自增主键：
- `SERIAL` / `BIGSERIAL`
- `GENERATED BY DEFAULT AS IDENTITY`（某些迁移工具会生成）

当前 db9-server 的现状：
- 内部存在“按 table_id 的自增”（`store.next_sequence_value(txn, schema.table_id)`，见 `src/sql/dml.rs`、`src/sql/executor.rs`），可支撑 INSERT 时生成自增值
- 但：
  - `CREATE SEQUENCE` 是 no-op（`src/sql/executor.rs`）
  - `NEXTVAL/CURRVAL/SETVAL` 是 stub（`src/sql/expr.rs:1629`）
  - `DROP SEQUENCE` 在 `Statement::Drop` 中直接返回 Empty（`src/sql/executor.rs`）

这会导致：
- 迁移工具/ORM 的 introspection 查询无法得到一致的 “sequence object” 视图
- 直接使用 `nextval()/setval()` 的迁移脚本无法工作

## 目标（MVP）

- 支持 `CREATE SEQUENCE / DROP SEQUENCE`
- 支持 `nextval(text|regclass)` / `currval(text|regclass)` / `setval(text|regclass, value[, is_called])`
- SERIAL/IDENTITY 列：
  - 在 `information_schema.columns.column_default` 中返回 `nextval('..._seq'::regclass)` 的同时，**该 sequence 必须真实存在**
  - INSERT 时生成的值与 `nextval`/`setval` 对同一序列一致
- `currval` 语义：仅在本 session 调用过 `nextval` 后才可用（否则报错）

## 非目标（MVP 不做）

- 完整 `ALTER SEQUENCE` 选项集合（只做迁移常见子集）
- 序列 cache/logging/persistence 细节完全对齐 PG（先保证语义正确）

## 设计概览

### 1) 存储层：Sequence Catalog

新增元数据 key：
- `_sys_seq_{schema}.{name}` -> `SequenceDef`

建议结构：

```rust
struct SequenceDef {
  schema: String,
  name: String,
  last_value: i64,
  increment: i64,     // default 1
  min_value: i64,     // default 1
  max_value: i64,     // default i64::MAX
  is_cycled: bool,    // default false
  is_called: bool,    // 用于 setval(..., is_called)
  owned_by: Option<(String /* table */, String /* column */)>,
}
```

并提供：
- `create_sequence(txn, def)`
- `drop_sequence(txn, full_name)`
- `nextval(txn, full_name) -> i64`
- `setval(txn, full_name, value, is_called)`

### 2) SERIAL/IDENTITY 的落地策略：与现有实现对齐

为了避免破坏现有 “table_id -> next_sequence_value” 的实现与性能路径，建议采用**桥接**策略：

#### 方案 A（推荐）：将现有 table_id 自增映射为隐式 sequence object

- SERIAL 列仍使用现有的内部 key（按 table_id）生成值
- 同时在 `CREATE TABLE` 时创建一个 “sequence 对象”：
  - 默认名：`{table}_{column}_seq`（PG 习惯）
  - `owned_by = (table, column)`
  - 该对象的 `last_value` 直接复用/映射到现有内部 key（避免双写）

实现方式：
- `SequenceDef` 不直接存 `last_value`，而是存一个 `backing`：
  - `Backing::TableId(table_id)`（复用现有 `_sys_seq_{table_id}` 或类似内部实现）
  - `Backing::Standalone(seq_key)`（独立序列）

这样：
- `INSERT` 走旧逻辑（高性能）
- `nextval()`/`setval()` 调用走新对象，但最终读写同一 backing

#### 方案 B：彻底迁移到 sequence object（后续）

把 `store.next_sequence_value(txn, table_id)` 改为按 sequence name 存储与递增。改动面更大，建议在 A 稳定后再做。

### 3) SQL 函数：nextval/currval/setval

在 `src/sql/expr.rs`：
- 用真实实现替换现有 stub
- 参数解析：
  - 允许 `'seq'`、`'seq'::regclass`（可通过字符串裁剪去掉 `::regclass`）
  - schema 省略时按 session search_path 解析（见 schema/search_path 设计）

`currval`：
- session 级缓存：`Session` 保存 `last_sequence_values: HashMap<seq_full_name, i64>`
- `nextval` 更新缓存；`currval` 读取缓存，不存在则报错

### 4) DDL：CREATE/DROP SEQUENCE

在 `Executor` 的 statement dispatch：
- `Statement::CreateSequence`：创建 `SequenceDef`
  - 解析常见选项：`START WITH`、`INCREMENT BY`（其它先忽略）
- `DROP SEQUENCE`：删除对象

并更新 pg_catalog 输出：
- `pg_class` 增加 `relkind='S'` 的行
- `pg_sequence`/`pg_depend` 可选（先按 ORM 需要补）

## 实现步骤（建议）

1. 实现 standalone sequence 的存储与 nextval/currval/setval（含 session cache）
2. 让 SERIAL/IDENTITY 创建隐式 sequence object（桥接 backing）
3. 补齐 `CREATE SEQUENCE` / `DROP SEQUENCE` 与 pg_catalog 输出

- `SELECT setval('s', 10); SELECT nextval('s');`（校验 10/11 的 is_called 行为）
- SERIAL：
  - `CREATE TABLE t (id SERIAL PRIMARY KEY, v INT);`
  - 连续插入不指定 id，id 递增
  - `SELECT nextval('t_id_seq');` 与插入生成值一致

建议新增一个 Python 集成测试（或扩展 `scripts/integration_test.py`）做跨连接验证：
