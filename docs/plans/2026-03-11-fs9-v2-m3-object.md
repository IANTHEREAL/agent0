# fs9 v2 M3: Object Backend in Server

Date: 2026-03-11

This note records the local implementation progress for **M3** of fs9 v2:

- `DataRef::Object` storage in S3
- hidden staging + atomic publish for object-backed writes
- object lifecycle cleanup and retry scaffolding

Design source of truth:

- `c4pt0r/db9-server#1752` consolidated design comment (`4039365600`)
- Local copy: `docs/design/29_fs9_v2_tikv_metadata_s3_packfiles.md`
- Execution plan: `docs/plans/2026-03-11-fs9-v2-implementation-plan.md`

## Goals (M3)

- Add an S3-backed storage path for large files routed to `DataRef::Object`.
- Preserve current fs9 publish semantics:
  - write to hidden staging state first
  - publish path metadata atomically in TiKV
  - defer old object cleanup through lifecycle GC
- Make sealed-object mutation boundaries explicit for Phase 1.
- Keep no-S3 behavior unchanged.

## Implementation Summary

### New S3 Client

- `src/extensions/fs/s3.rs`
  - Adds `FsS3Client` over the AWS Rust SDK.
  - Implements:
    - `get_object_bytes`
    - `get_object_range_bytes`
    - `get_object_stream`
    - `head_object`
    - `delete_object`
    - multipart upload lifecycle:
      - `create_multipart_upload`
      - `upload_part`
      - `complete_multipart_upload`
      - `abort_multipart_upload`

### Config and Build Resolution

- `src/extensions/fs/config.rs`
  - Adds fs9 object-route configuration:
    - `FS9_OBJECT_MIN`
    - `FS9_S3_BUCKET`
    - `FS9_S3_REGION`
    - `FS9_S3_ENDPOINT`
    - `FS9_S3_PREFIX`
    - `FS9_S3_FORCE_PATH_STYLE`
    - `FS9_S3_MULTIPART_PART`
    - `FS9_S3_HEAD_RETRY_ATTEMPTS`
    - `FS9_S3_HEAD_RETRY_BASE_MS`
    - `FS9_TIKV_COMMIT_RETRY_ATTEMPTS`
    - `FS9_TIKV_COMMIT_RETRY_BASE_MS`
    - `FS9_GC_INTERVAL_SECS`
    - `FS9_GC_INITIAL_JITTER_MS`
- `.cargo/config.toml`
  - Forces Cargo to prefer Rust-1.88-compatible transitive versions via:
    - `resolver.incompatible-rust-versions = "fallback"`

### Object Read Path

- `read_file`
  - object-backed files use S3 GET
- `read_file_at`
  - object-backed files use S3 range GET
- `read_file_stream`
  - object-backed files stream from `get_object_stream()` instead of materializing the full object in TiKV-backed code paths

### Object Write Path

- `write_file`
  - routes files at or above `FS9_OBJECT_MIN` to the object write stream when S3 is enabled
- `begin_write_stream`
  - creates a hidden staging inode
  - creates multipart upload state in S3
  - marks `_fs_L{inode}` as `Uploading`
- `EmbeddedObjectWriteStream`
  - uploads parts incrementally to S3
  - performs HEAD verification before publish
  - persists final `DataRef::Object` metadata
  - publishes through the existing hidden-staging path

### Retry / Lifecycle / Cleanup

- HEAD verification retry is implemented before object publish.
- TiKV optimistic write-conflict retry is implemented for:
  - object staging transition from `Uploading` to `Committing`
  - final `publish_staged_write` transaction
- lifecycle GC covers:
  - stale `Uploading`
  - stale `Committing`
  - deferred `Deleting`
- background lifecycle GC uses startup jitter plus periodic sweeps.

### Mutation Boundaries

- `write_file_at`, `append_file`, `truncate`
  - reject `DataRef::Object`
  - reject `DataRef::PackEntry`
- This keeps Phase-1 sealed-object semantics explicit instead of silently emulating pagefs mutation behavior on S3 objects.
