# Issue #1949 Implementation: Unified resolve_custom_type

## Background
PR #1947 failed after 34 commits and 7 QG FAIL reviews. Expert panel identified root cause: **6 separate code paths** independently resolve `DataType::Custom`, each with different fallback behavior.

## Your Task
Create a UNIFIED `resolve_custom_type` function with 4-step pipeline:

### 4-Step Pipeline
1. **Serial check** — DdlColumn context expands serial pseudo-types to (Int32/Int64, true). NonDdl/DdlOther: serial names go through normal resolution.
2. **Catalog lookup** — if catalog provided, look up type name. Found UDT? Return UserDefined(full_name).
3. **Built-in mapping** — handle jsonb, tsvector, name, timestamptz, reg*, oid, etc.
4. **Unknown** — raise SqlError 42704 "type X does not exist" (NO silent Text fallback).

### Files to Modify
1. `types/mapping.rs` — Create `resolve_custom_type()`, update `convert_custom_type`
2. `ddl/mod.rs` — Update `resolve_column_data_type`, `resolve_nested_column_data_type`
3. `analyzer/expr/mod.rs` — Update `resolve_sql_data_type`
4. `prepared.rs` — Update `execute_sql_prepare_statement`
5. `udt/mod.rs` — Update `execute_create_type`

### Key Design Decisions
- Catalog is optional — paths without catalog must gain it or document limitation
- Serial is ONLY special in DdlColumn context
- Built-in check comes AFTER catalog lookup (PostgreSQL order)
- NO silent Text fallback — unknown types raise 42704
